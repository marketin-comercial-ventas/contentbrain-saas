## Alcance

Resultado: repo con stack fijado y verificable, entorno de pruebas con
PostgreSQL real aislado, migración inicial, comandos de calidad reales,
`quality:gate` ejecutable, CI local y evidencia con formato canónico.

Entregables concretos:

1. `package.json` con versiones fijadas (sin `latest`) y `pnpm-lock.yaml`
   versionado; `pnpm install` reproducible.
2. App Next.js (App Router, TS estricto) que arranca y compila en build de
   producción.
3. PostgreSQL de pruebas real e aislado: **base de datos dedicada por
   ejecución** (`app_test_*`) creada y eliminada en global-setup/teardown.
   Motor elegido por `TEST_DATABASE_URL` (servicio PostgreSQL local) y, si no
   está definido, `embedded-postgres` (binarios locales). Ver
   «Cambios acordados durante la ejecución».
4. Pipeline Drizzle: schema inicial, `drizzle-kit generate`, runner de
   migraciones que registra su aplicación y se ejecuta en base vacía y en base
   con datos previos.
5. Scripts reales: `lint`, `typecheck`, `test:unit`, `test:integration`,
   `test:e2e`, `test:security`, `test:regression`, `build`, `quality:gate`.
6. `quality:gate`: agrega resultados, escribe reporte estructurado, sale con
   código ≠ 0 ante fallo o evidencia ausente, comprueba existencia de veredicto
   QA independiente y **no** autoemite aprobación.
7. Modo autotest del gate: con una falla inyectada (flag) el gate devuelve
   fallo; sin fallas, pasa. Evidencia de ambos escenarios.
8. CI en `.github/workflows/ci.yml` ejecutando las mismas etapas.
9. Evidencia en `docs/qa/f00/<commit>/`.

## Contratos

- `GET /api/health` → `200 { status: "ok", service, version, timestamp }`;
  sin internals, sin secretos, sin detalle de entorno en producción.
- `src/shared/contracts/health.ts`: esquema Zod de la respuesta (fuente única
  para servidor y tests).
- `src/server/db/client.ts`: constructor de conexión a partir de
  `DATABASE_URL`; sin credenciales en código.
- Runner de migraciones: `scripts/db-migrate.mjs` aplica `drizzle` SQL
  pendientes y registra cada una aplicada (hash + fecha) en
  `schema_migrations`; re-ejecutar sin pendientes es exitoso y no repite.

## Riesgos

1. `embedded-postgres` no puede arrancar desde sesión de administradora en
   Windows (restricción de PostgreSQL) → resuelto: servicio PostgreSQL local
   + base dedicada por ejecución; `embedded-postgres` queda como respaldo
   (CI/sesión no elevada).
2. Descarga de Chromium para Playwright falla → bloqueo de CA-02/e2e.
3. Incompatibilidad de versiones (TS 7 vs typescript-eslint <6.1) → fijado
   TS 5.9.3; si aparece otro conflicto, se resuelve por ADR.
4. QA independiente ausente → el gate de F00 termina BLOCKED aunque lo
   automatizado pase; no se simula revisor.
5. Vercel/GitHub sin credenciales → CA-06 parcial, bloqueo aceptado por el
   propietario.

## Cambios acordados durante la ejecución

- **2026-10-07 — estrategia de BD de pruebas:** `embedded-postgres` aborta
  con «Execution of PostgreSQL by a user with administrative permissions is
  not permitted» en esta sesión (admin). Acordado con el propietario: instalar
  PostgreSQL 17 como **servicio** con winget y crear una **base dedicada por
  ejecución** (`app_test_*`, se crea y borra en global-setup/teardown);
  `TEST_DATABASE_URL` la activa y `embedded-postgres` queda como respaldo
  automático cuando no está definida (CI, sesión no elevada). El aislamiento
  exigido por REQ-F00-03 se cumple por base dedicada por ejecución sobre una
  instancia local sin datos de producción.
